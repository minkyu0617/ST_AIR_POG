# 08. 멀티플레이 아키텍처

## 8.1 토폴로지 결정

### 결론: **Steam 릴레이 기반 리슨 서버(Listen Server) + 서버 권위**

```
        ┌──────────────────────────────────────┐
        │        Steam Datagram Relay (SDR)    │  ← IP 노출 없음, DDoS 방어, NAT 통과
        └──────────────┬───────────────────────┘
                       │
        ┌──────────────▼───────────────┐
        │   호스트 (방장) = 리슨 서버    │  ← 게임 권위(Authority)
        │   시뮬레이션 · 히트 판정       │
        └──┬────────┬────────┬─────────┘
           │        │        │
        ┌──▼──┐  ┌──▼──┐  ┌──▼──┐
        │ C1  │  │ C2  │  │ C9  │   ← 클라이언트 예측 + 서버 화해
        └─────┘  └─────┘  └─────┘
```

### 근거
| 방식 | 서버 비용 | 치팅 내성 | 구현 난이도 | 판단 |
|---|---|---|---|---|
| P2P 풀메시 | 0 | 최악 | 중 | ❌ |
| **리슨 서버 + SDR** | **0** | 중 (호스트 어드밴티지 존재) | 중 | ✅ **v1.0 채택** |
| 전용 서버 | 월 ₩150~400만 (동접 500 기준) | 상 | 상 | v1.1 랭크전용 옵션 |

**핵심 판단**: 인디 멀티 게임의 90%는 출시 3개월 후 동접 50 미만입니다. 그 상태에서 전용 서버 비용은 게임을 죽이는 고정비가 됩니다. **리슨 서버로 고정비 0을 확보하고, 동접이 실제로 나오면 그때 전용 서버를 추가**하는 것이 유일하게 합리적인 순서입니다.
Steam Datagram Relay는 무료이며 IP 노출/DDoS/NAT 문제를 한 번에 해결하므로, P2P의 실질적 단점 대부분이 제거됩니다.

### 호스트 이관 (Host Migration)
- 호스트 이탈 시 **경기 중이면 해당 경기는 종료**하고 결과를 확정한 뒤 로비로 복귀시킵니다.
- 로비 상태에서는 재접속 없이 방장만 자동 위임됩니다.
- 경기 중 이관은 상태 동기화 복잡도 대비 이득이 적어 **v1.0 범위에서 제외**합니다. 대신 이탈 시 XP/보상은 정상 지급하여 유저 손해를 없앱니다.

## 8.2 네트워크 모델

| 항목 | 값 |
|---|---|
| 서버 틱레이트 | 30 Hz (물리 시뮬 60 Hz, 스냅샷 30 Hz) |
| 클라이언트 입력 전송 | 60 Hz (입력 버퍼 3프레임 중복 전송으로 패킷 손실 대응) |
| 프로토콜 | UDP (SteamNetworkingSockets) |
| 대역폭 목표 | 상행 12 KB/s, 하행 45 KB/s @ 10인 |
| 목표 RTT 허용치 | 200 ms까지 쾌적, 300 ms까지 플레이 가능 |

### 클라이언트 예측 & 화해 (Prediction & Reconciliation)
```
클라 입력(프레임 N) → 즉시 로컬 시뮬 적용 (예측)
                   → 서버 전송
서버 → 권위 시뮬 → 스냅샷(프레임 N 처리 결과) 회신
클라 → 서버 상태와 예측 이력 비교
     → 오차 > 임계값이면 롤백 후 재시뮬 (Replay)
     → 오차 < 임계값이면 부드럽게 보정 (Smoothing, 0.15s 블렌딩)
```
- 비행기는 **관성이 크고 방향 급변이 적어** FPS보다 예측이 잘 맞습니다. 이 게임의 장르적 이점입니다.
- 오차 임계값: 위치 50 cm / 회전 2°. 미만은 화면 튐 방지를 위해 무시하고 블렌딩합니다.

### 원격 기체 보간
- 다른 플레이어는 **100 ms 과거 상태를 보간 재생**(interpolation delay)하여 부드럽게 표시합니다.
- 패킷 유실 시 최대 300 ms까지 외삽(extrapolation), 이후 정지 후 스냅.

### 랙 보상
- 히트 판정 시 서버는 발사자 RTT/2 만큼 되감은 대상 히트박스로 판정 (상한 200 ms).
- 되감기 이력은 1초 링버퍼로 보관.

## 8.3 리플리케이션 우선순위

10인 × 다수 발사체를 30Hz로 전부 보내면 대역폭이 터집니다. **관련성(Relevancy) 기반 우선순위**를 둡니다.

| 우선도 | 대상 | 갱신 빈도 |
|---|---|---|
| 최상 | 자기 기체 상태 보정 | 30 Hz |
| 상 | 3 km 내 기체, 나를 향한 발사체 | 30 Hz |
| 중 | 3~8 km 기체, POI 상태 | 10 Hz |
| 하 | 8 km 초과 기체(미니맵 표시용 위치만) | 2 Hz |
| 이벤트 | 격추/아이템 획득/핑/토스트 | 신뢰성 채널, 발생 시 1회 |

- 원거리 기체는 **위치·속도만** 보내고 애니메이션/이펙트는 로컬에서 생성합니다.
- 발사체는 개별 오브젝트를 복제하지 않고 **"발사 이벤트 + 결정론적 궤적"** 으로 전송합니다 (기총·로켓). 유도 미사일만 실제 복제.

## 8.4 방(Room) 시스템 — 상태 동기화

[04번 문서 4.6](04_game_modes.md)의 규칙을 네트워크 관점에서 정의합니다.

### 서버 권위 상태
```
RoomState {
  hostId          : PlayerId
  mode            : SINGLE_RACE | TEAM_RACE | FFA_BATTLE | TEAM_BATTLE
  mapId           : MapId
  teamCount       : 2..5
  players         : [ { id, nickname, team, isReady, ping, aircraftId } ]
  lockState       : OPEN | LOCKED | STARTING | IN_GAME
  settingsVersion : uint32     // 변경마다 증가
}
```

### 잠금 규칙의 서버 검증
```
onSettingChange(request):
    if roomState.lockState != OPEN:         reject("LOCKED")     # ← 서버가 최종 판단
    if request.senderId != roomState.hostId: reject("NOT_HOST")
    apply(request)
    roomState.settingsVersion++
    for p in players: p.isReady = false      # 준비 자동 해제
    broadcast(ToastEvent{ type, before, after })
    broadcast(RoomStateUpdate)
```
> **UI 비활성화만으로는 부족합니다.** 클라이언트 UI는 조작 가능하므로 반드시 서버에서 `lockState`를 재검증해야 하며, 이것이 "전원 준비 상태에서 설정 변경 불가"의 실제 구현 지점입니다.

### 경합 처리 (Race Condition)
가장 위험한 시나리오: **마지막 플레이어가 준비를 누르는 순간 방장이 맵을 변경**.

- 모든 설정 변경/준비 요청은 클라이언트가 알고 있는 `settingsVersion`을 함께 보냅니다.
- 서버의 현재 버전과 다르면 **요청을 거부**하고 최신 상태를 회신합니다.
- 준비 요청이 거부되면 클라이언트는 토스트로 알립니다: *"설정이 변경되어 준비가 취소되었습니다."*
- 이로써 "내가 준비한 시점의 설정"과 "실제 시작될 설정"의 불일치가 원천 차단됩니다.

### 시작 시퀀스 동기화
```
방장 START → 서버: lockState = STARTING
           → 전원에게 StartMatch{ serverStartTimeUtc, seed, mapId, mode }
           → 각 클라이언트 로딩 (최대 20초 대기)
           → 전원 로딩 완료 or 타임아웃
           → 서버 시각 기준 T-3 카운트다운 시작
```
- 카운트다운은 **서버 시각(UTC) 기준**으로 각 클라이언트가 자체 계산 → RTT 차이로 인한 스타트 불공정 제거.
- 최고 RTT 플레이어 기준 **+200 ms 버퍼**를 두고 입력 활성화 시점을 맞춥니다.
- 20초 내 로딩 실패자는 경기에서 제외하고 나머지로 시작합니다 (한 명 때문에 전원 대기 금지).

## 8.5 매치메이킹 & 방 찾기

| 기능 | 구현 |
|---|---|
| 방 목록 | Steam Lobby Matchmaking API (필터: 모드/맵/인원/핑) |
| 빠른 시작 | 조건 맞는 방 자동 입장, 없으면 신규 생성 |
| 친구 초대 | Steam 오버레이 초대 + Rich Presence + 커맨드라인 조인 |
| 비밀방 | 6자리 코드 입장 |
| 지역 | Steam 릴레이 자동 라우팅 (한국/일본/미서부/유럽) |

**동접 부족 대응 (필수 설계)**
- 방에 인원이 부족하면 **AI 봇으로 채우는 옵션**을 방장이 켤 수 있게 합니다. 봇 난이도 3단계.
- 이는 선택 기능이 아니라 **생존 기능**입니다. 출시 6개월 후 새벽 시간대에 방이 안 차서 게임을 못 하는 상황이 리텐션을 끝냅니다.

## 8.6 치팅 대응 (리슨 서버의 한계 인정)

| 위협 | 대응 |
|---|---|
| 속도/텔레포트 핵 | 서버 이동 검증 (최대 속도·가속 한계 초과 시 보정 및 로그) |
| 무한 아이템 | 아이템 소비는 서버 권위, 클라 요청은 힌트일 뿐 |
| 에임봇 | 리슨 서버에서 완전 차단 불가 — **신고 기능 + 호스트 강퇴 권한**으로 대응 |
| 호스트 어드밴티지 | 호스트에게도 **인위적 입력 지연(평균 RTT/2, 최대 40ms)** 을 적용해 공정성 확보 |
| 리더보드 조작 | 싱글 기록은 **입력 스트림 리플레이를 함께 제출**, 서버에서 재시뮬 검증 후 등재 |

- Steam VAC는 적용하지 않습니다 (리슨 서버 구조에서 실효성 낮고 오탐 리스크가 큼).
- **랭크 시스템이 없는 v1.0에서는 치팅의 실질 피해가 제한적**이며, 랭크 도입 시 전용 서버와 함께 대응 수준을 올립니다.

## 8.7 서버 비용 시나리오

| 단계 | 구성 | 월 비용 |
|---|---|---|
| v1.0 (리슨 서버 + SDR) | Steam 인프라만 사용 | **₩0** |
| 백엔드 (리더보드/통계) | Steam Leaderboards + Stats API | **₩0** |
| v1.1 랭크 (전용 서버) | 동접 300 기준, 4 vCPU × 6대 (KR/JP/US/EU) | 약 ₩180만 |
| 커스텀 백엔드 (선택) | 소규모 API 서버 + DB | 약 ₩30만 |

**결론: v1.0의 운영 고정비는 사실상 0원**입니다. 이는 인디 프로젝트의 생존 기간을 결정하는 가장 중요한 구조적 결정입니다.
